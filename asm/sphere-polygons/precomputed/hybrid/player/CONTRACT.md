# PAL playback measurement

All players show the same64-frame checker loop. The default delta player reads HD64; the independent-frame comparison players read HC64. The font remains the original2,048-byte mathematical font. These movie players contain no runtime geometry calculation.

Run `node prepare-assets.cjs` from this directory once. Shared immutable assets are in `build/assets/`: checker-64.hc64, checker-64-raw.hc64, checker-64-smooth-delta1-lag1.hd64, font.bin and their layout metadata. The separate `build/reference/` is verifier input only and must never be imported into a player.

HD64 uses a14-byte header followed by50 row-layout bytes. Each frame has a16-bit payload length with bit15 marking a key. The current movie contains one HC64-style initial key and63 predictive records. Predictive packets use the top two opcode bits for skip/literal/repeat and the low six bits for length minus one. They cover exactly1,000 character positions. Lag-one synchronization copies the real front buffer before applying a predictive record. The decoded initial key is cached once; copying that cache at each wrap is timed. Every other record must be predictive in this specialized player.

HC64 global header is12bytes, followed by50bytes of row spans. First frame begins at offset62. Each frame has fillLengthLE16, edgeLengthLE16, fill payload, edge payload. The compact fill is PackBits expanding to60bytes. The edge payload begins with60raw presence-map bytes, then exact glyph codes in ascending screen order. Iterate475 selected cells in row-span order. The tail padding bits are ignored. Fill bits select glyph0 or15; edge presence overrides that value with the next glyph. The maximum edge-glyph count is below256, so an8-bit glyph index is valid.

Prefer the compact file for comparable size measurements. The raw-fill file is provided for a separately reported speed/space tradeoff. A static destination layout or offset table may be generated from the serialized metadata, but its bytes count toward the player footprint. Do not generate or embed per-frame character screens in code.

Required labels: render_start, render_end, frame_done, frame_index, frame_counter, front_screen_hi, back_screen_hi. frame_counter is16bit. At frame_done, frame_index identifies the screen that was just presented; advance the index after this label. Frame0 is presented first. After frame63, restore the first encoded frame pointer and index0.

Use bank0 hires text, white character color, black background, font$2000 and screens$0400/$0c00. Initialize both complete screen buffers, color RAM, VIC and interrupt state. Swap only at a PAL raster wrap after decoding finishes. The independent-frame baselines use their natural raster-wait cadence. The compact delta player targets two PAL fields per image; its faster cached frame0 waits an additional field to preserve that cadence. Per-frame parsing, synchronization and screen writes occur between render_start and render_end. Startup-only initial-key decoding is described separately and is not a recurring frame cost.

Each variant builds its own build/player.prg and build/main.sym. Code and emitted load data should stay outside I/O and hardware vectors. The root verifier owns VICE processes and compares all1,000 screen bytes, font bytes, VIC setup, loop wrap and actual screenshots. PAL render clocks include VIC stalls; presentation clocks include the raster wait.
