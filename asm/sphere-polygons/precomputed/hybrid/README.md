# Precomputed checker-sphere formats

This directory compares exact ways to store and replay checker-sphere character
screens. Each decoded image is a 40×25 screen of 1,000 glyph indices using the
same fixed 2,048-byte font. Glyph 0 is empty, glyph 15 is solid, and the other
glyphs describe boundaries. Compression preserves the character screens
exactly; it does not improve or approximate their geometry.

The native players currently decode **independent HC64 images**. Inter-frame
delta streams are measured and verified offline; they are not the format used
by the running C64 player. Native playback, memory maps and PAL measurements
are documented in the [player README](player/README.md), with implementation
details in the [compact](player/compact/README.md),
[fused](player/fused/README.md) and [unrolled](player/unrolled/README.md) player
notes.

## Two motion sequences

The original packing experiments use the 256-image tumble from
[common.cjs](common.cjs): yaw, pitch and roll start at `(0,24,0)` and advance by
`(2,1,1)` in 8-bit angle units. The 64-image comparison takes every fourth pose,
so its steps are `(8,4,4)`. Results for this sequence are recorded in
[`build/study.json`](build/study.json),
[`build/delta-study.json`](build/delta-study.json) and
[`build/codegen-report.json`](build/codegen-report.json).

The current player uses the separate smoother sequence generated by
[player/motion.cjs](player/motion.cjs). It holds pitch at 22° and roll at 12°,
advancing yaw by 0.9375° per image. A 64-image loop covers the checker's 60°
rotational symmetry period; its endpoint is checked to match the start exactly.
Angles are evaluated with finer precision than the original 8-bit angle steps,
then projected coordinates are quantized for the existing character renderer.
This is an offline movie generator: no geometry runs during C64 playback.

The smooth-motion delta report is
[`player/build/motion-delta.json`](player/build/motion-delta.json), produced by
[player/motion-delta.cjs](player/motion-delta.cjs). Its results must not be mixed
with the original tumble's size measurements.

## Independent images: fill plus exact edges

The winning tested independent format separates each image into a binary fill
layer and an exact edge layer. A fixed circle layout contains 475 character
cells. Its 50 metadata bytes store a start column and length for each of 25
rows. Cells outside this layout stay empty after both screen buffers are
cleared once.

The fill layer has one bit per layout cell: 0 expands to glyph 0, and 1 expands
to glyph 15. A cell that will receive an edge glyph leaves its underlying fill
bit unconstrained. The offline encoder chooses these free bits to improve
compression, while preserving every actual empty and full cell. The 475 bits
occupy 60 packed bytes, most significant bit first; the five unused padding
bits do not produce cells. The selected fill codec, `wildcard-packbits`, encodes
these bytes with literal and repeat packets.

The edge layer begins with an uncompressed 60-byte presence mask over the same
475 cells, followed by one exact glyph byte for each set bit in screen order.
Decoding first expands the fill and then replaces the marked cells. The edge
mask has no free bits. Compressing that mask added packet overhead on this
corpus, so the raw mask was smaller overall.

The selected HC64 container contains:

| Part | Serialized bytes |
| --- | ---: |
| Magic, version, dimensions, image count, layout and codec IDs | 12 once |
| Circle row-span metadata | 50 once |
| Fill payload length and edge payload length, both little-endian 16-bit | 4 per image |
| PackBits fill payload | Variable |
| Raw edge-presence mask | 60 per image |
| Exact edge glyphs | One per marked cell |

The first image therefore starts at byte 62. No per-image rectangle, hidden
dictionary or random-access table is assumed. A seek index would be an
additional cost. The font is shared and reported separately.

The format is implemented by [container.cjs](container.cjs),
[fill.cjs](fill.cjs), [edge-maps.cjs](edge-maps.cjs) and
[common.cjs](common.cjs). The [format contract](CONTRACT.md),
[fill notes](notes-fill.md), [edge notes](notes-edges.md) and
[presence-map notes](notes-edge-maps.md) describe the other measured choices.

## Original tumble: independent-format results

These are complete serialized containers from `build/study.json`, including
their shared headers, layout metadata and image framing. They exclude the
font, decoder and optional seek index. The 64-image column samples the full
256-image tumble; it is not the newer smooth player sequence.

| Format | 256 images | 64 images |
| --- | ---: | ---: |
| Common-character RLE | 95,132 B | 23,832 B |
| Strict alternating pairs, ordinary literals allowed | 105,243 B | 26,364 B |
| Strict alternating pairs, edge-only literals | 121,812 B | 30,473 B |
| Circle fill/edge HC64 | **78,700 B** | **19,773 B** |

The selected HC64 format averages 307.42 bytes per image for the 256-image
sequence, including its share of all container overhead. It is 17.27% smaller
than the measured full-screen RLE container.

[baseline-rle.cjs](baseline-rle.cjs) uses one-byte run packets for common glyphs
0 and 15, literal packets for arbitrary glyphs, and repeat packets for other
repeated codes. All packet lengths are 1–64 cells. It is a stronger reference
than plain raw 1,000-byte images or a generic two-byte count/value RLE.

The alternating-stream experiment starts with empty fill, emits alternating
empty/full runs, and inserts literal glyphs between them. The strict grammar
is `[runLength][literalCount][literalGlyphs...]`; zero-length runs still change
the fill phase. Permitting a genuine empty or full source cell in the literal
section can repair the phase without inventing output cells. This saves
16,569 bytes over edge-only strict pairs in the 256-image test, but the result
remains larger than the binary-fill/presence-mask hybrid. An escaped grammar
was also measured. See [alternating.cjs](alternating.cjs) and
[notes-alternating.md](notes-alternating.md) for the exact grammars and proofs.

## Inter-frame skip/render streams

Two patch families are implemented in [delta.cjs](delta.cjs): skip/literal
length pairs encoded with unsigned LEB128, and one-byte operation packets for
skip, literal or repeat spans of 1–64 cells. Their offline dynamic programs may
include unchanged cells in a literal when that reduces the complete packet
cost. Blank and full glyphs remain ordinary writable values, so an edge that
disappears is correctly cleared.

The current [HD64 container](delta-wire.cjs) uses compressed HC64-style key
images plus patches. Its shared header is 14 bytes, followed by the same
50-byte layout metadata. Each image has a 16-bit payload length with its high
bit selecting key or delta. A key payload contains its fill length, fill bytes
and edge bytes. The first one or two images are keys, depending on reference
lag; these keys are decoded again when the loop restarts. All reported sizes
include these fields and required keys.

Lag 1 references the immediately preceding decoded image, `t−1`. Lag 2
references `t−2`, which is the existing content of the destination screen when
two screens alternate. Lag 1 therefore needs a canonical previous image or
additional screen synchronization in a double-buffered native player. The
smaller lag-1 stream alone does not establish a faster or smaller complete
player.

For the **original tumble**, the current hybrid-key results in
`build/delta-study.json` are:

| Sequence | Independent HC64 | Best lag 1 | Best lag 2 |
| --- | ---: | ---: | ---: |
| 256 images | 78,700 B | 78,631 B: 250 keys, 6 patches | 78,702 B: all keys |
| 64 images | 19,773 B | 19,775 B: all keys | 19,775 B: all keys |

This motion provides almost no useful size reduction over independent hybrid
images. The extra two header bytes explain the slight increase when the
adaptive encoder chooses only keys.

For the **new smooth motion**, `player/build/motion-delta.json` records:

| Representation | 64-image bytes | Keys / patches | Saving against independent |
| --- | ---: | ---: | ---: |
| Independent HC64 | 19,096 B | 64 / 0 | — |
| Best lag 1, 64-cell opcode packets | 15,169 B | 1 / 63 | **20.56%** |
| Best lag 2, adaptive opcode packets | 19,067 B | 56 / 8 | **0.15%** |

The roughly 21% lag-1 saving is specific to this smoother trajectory. Its mean
change is about 91.7 cells between consecutive images, compared with 131.3
cells across a lag of two. The native players continue to use the independent
19,096-byte HC64 asset. No native delta decoder or delta FPS result is claimed.

[delta-study.cjs](delta-study.cjs) measures the original sequence with hybrid
keys, and [player/motion-delta.cjs](player/motion-delta.cjs) applies the same
container to the smoother sequence. Both verify actual serialized bytes over
three loops, maintaining real lag-2 buffer history. The existing
[notes-delta.md](notes-delta.md) describes the patch grammars and an **earlier
experiment with larger common-character RLE keys**. Its old totals and DC64
framing are separate from the current HD64 tables above.

## Generated 6502 per image

The bounded [code-generation study](codegen-study.cjs) emitted and executed
actual 6502 instructions for the original tumble. Strategy A groups cells by
glyph, loads that glyph once, and emits an absolute store per cell. Strategy B
also uses shared per-row fill loops when a contiguous same-glyph run makes a
seven-byte helper call sequence smaller than direct stores.

| Original sequence representation | 64 images | 256 images |
| --- | ---: | ---: |
| A: grouped direct stores | 99,052 B | 396,280 B |
| B: shared row fills | 85,047 B | 339,332 B |
| Independent HC64 plus actual fused decoder, lookup/layout code and BASIC stub | 36,173 B | 95,100 B |

Generated-code totals include a real 32-byte screen initializer, 400 bytes of
row helpers for strategy B, a 12-byte header and three-byte file offsets per
image. The common font is excluded on both sides. Even the 64-image generated
archive exceeds 64 KiB; a live loader or bank/overlay dispatcher is not supplied
or charged. These are favorable storage lower bounds for those code strategies.

Once resident, the 64-image routines average 2,024 CPU instruction cycles for
A and 4,267 for B. Those py65 timings exclude code loading, VIC stalls,
interrupts and presentation, so they are not native FPS measurements. The
study verified 644 executions and 644,000 screen bytes, including loop wrap.
Full costs and limitations are in [notes-codegen.md](notes-codegen.md).

A more elaborate shared shape dictionary could improve on these two simple
strategies; this was not a global optimization search. Line orientation can be
precomputed, but glyph selection also depends on phase within the cell, fill
polarity, endpoints, clipping, corners and crossings. A native `JSR` already
costs three bytes before parameters, so a bytecoded display list can remain
smaller than a native call stream. The current fast HC64 decoders instead share
their destination-layout code across every image.

## Reports and verification

Generated reports and movie binaries live in ignored `build/` directories.
The original independent study reports 30,400 exact reconstructed images; the
current hybrid-key delta study compares 15,360,000 character bytes, and the
smooth-motion delta study compares 2,304,000 bytes across its tested policies
and three-loop decodes. These are host correctness and serialized-size
measurements. Native 6510 timing belongs to the separate player verification.

The main entry points are [study.cjs](study.cjs),
[verify-container.cjs](verify-container.cjs),
[delta-study.cjs](delta-study.cjs), and
[player/motion-delta.cjs](player/motion-delta.cjs). The
[player contract](player/CONTRACT.md) defines its native measurement boundary.
